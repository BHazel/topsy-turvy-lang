## 2. Non-Obvious Constraints

A new session must know these before touching the relevant code.

**Visual editor — port alignment is derived from `VisualPortRole`, never set explicitly**: `VisualGraphBuilder.MakePort` converts `VisualPortRole` → `PortAlignment` internally (`FlowIn` → Top, `FlowOut`/`BranchOut` → Bottom, `DataIn` → Left, `DataOut` → Right). Do not pass an alignment argument; there is no overload that accepts one.

**Visual editor — block closer pattern**: every block-level `Create*` method (Conditional, Loop, TryCatch, Switch, Guard) must (1) build all branches first while collecting each branch's tail node, (2) find `maxTailY = branches.Max(tail => tail.Position.Y)`, (3) place the closer node at `new Point(openerX, maxTailY + NodeLayoutContext.RowSpacing)`, (4) call `layout.AdvancePrimaryYTo(closerY + NodeLayoutContext.RowSpacing)`. Violating this order puts the closer at the same depth as mid-branch nodes.

**Visual editor — branch centering formula**: for `N` branches, branch `i` (0-based) is placed at `openerX + (i - (N-1)/2.0) * spacing`. Spacing constants: 660 px for Conditional and TryCatch (accommodates expression trees on ElseIf branches); 440 px for Switch. This keeps the opener visually centred above its branches.

**Visual editor — expression anchoring**: `CreateExpressionNode` places expression nodes at `(anchor.X - ExprColumnWidth, anchor.Y + portIndex * ExprPortSpacingY)` where `ExprColumnWidth = 210.0` and `ExprPortSpacingY = 80.0`. `portIndex` is the 0-based port slot on the consumer node. Always pass a non-null `anchor` equal to the consuming statement node's position.

**Visual editor — CSS class prefix**: all CSS classes for visual node rendering use the `visual-node-` prefix (e.g. `visual-node`, `visual-node-header`, `visual-node-flow-top`). Do not introduce `vn-` prefixed classes — that prefix was retired in the 2026-06-27 session.

**Visual editor — `VisualGraphBuilder` is a single file**: it is large (~1 100 lines) but splitting it into partial classes is deferred. When splitting, use: `VisualGraphBuilder.Statements.cs` and `VisualGraphBuilder.Expressions.cs`.

**Visual editor — `VisualGraphToAstConverter` reads only from the live diagram**: `Convert()` makes no reference to `originalProgram`. Sidebar nodes (floating declarations/imports with no incoming FlowIn link) are detected by `HasIncomingFlowLink(node)` which checks whether the node's `FlowIn` port has any links. Do not reintroduce an AST-backbone approach — factory-created nodes have no `AstNode` and would be silently lost.

**Visual editor — branch header `StatementType` sentinels must be skipped in `WalkFlowStatements`**: all 8 branch-header types are in the skip list: `"ConditionalTrueBranch"`, `"ConditionalElseIfBranch"`, `"ConditionalElseBranch"`, `"TryCatchSuccessBranch"`, `"TryCatchErrorBranch"`, `"SwitchCaseBranch"`, `"SwitchDefaultBranch"`, `"GuardElseBranch"`. When adding a new block type, add its branch-header sentinel here. `WalkFlowStatements` starts from `NextFlowNode(startNode)`, so passing a branch-header node as `startNode` is also safe — the first skipped `continue` handles it, but the skip list is a belt-and-suspenders guard for cases where the header ends up mid-walk.

**Visual editor — `VisualNodeFactory` must use `Keywords.TypeNames.*` constants, not raw strings**: `VisualTypeMaps.TypeToKeyword` uses `Keywords.TypeNames.*` throughout. New entries in `VisualTypeMaps` must follow the same rule — never write a Topsy Turvy type keyword as a string literal in this file.

**Visual editor — context menu CSS prefix is `visual-context-menu-`**: classes follow BEM: `visual-context-menu` (container), `visual-context-menu-section-label`, `visual-context-menu-item`, `visual-context-menu-item--danger` (modifier). Do not use the old `vcm-` prefix.

**Visual editor — `Node.Refresh()` is required for ZBD to re-render after property mutations**: Z.Blazor.Diagrams does not watch individual model properties. After any mutation of `TopsyTurvyVisualNodeModel` properties (title, subtitle, port list, etc.) via an editing control, call `this.Node.Refresh()` before `await OnNodeChanged.InvokeAsync()`. Without it, the diagram canvas will not re-render the node widget — changes appear to have no effect until the user interacts with the canvas.

**Visual editor — subscribe to `link.TargetAttached`, not `diagram.Links.Added`, for bidirectional validation**: at the point `Links.Added` fires, the user-drawn link's target is still a floating `PointAnchor`, not a `SinglePortAnchor`. Checking `link.Target is not SinglePortAnchor` will always return true and cause the validation to immediately reject (or skip) every new link. Subscribe to `link.TargetAttached` inside the `Links.Added` handler to validate only after the user completes the connection: `link.TargetAttached += (_, _) => { /* validate port role pair */ }`.

**Visual editor — Blazor CSS isolation does not apply to child component elements**: `VisualEditor.razor.css` is scoped to `VisualEditor.razor`'s own rendered elements only — it cannot style elements rendered by child components such as `VisualSymbolPanel`. To override MudBlazor styles inside a child component (e.g. `.mud-expand-panel-gutters` padding), add the rule to global `app.css` and qualify it with a CSS class on the parent wrapper (e.g. `.visual-symbol-panel .mud-expand-panel-gutters { padding: ... !important; }`). The `!important` is necessary because MudBlazor's component styles load with higher specificity than global rules.

**Visual editor — port naming conventions (Phase C)**: the following labels are canonical and must be used consistently across `VisualGraphBuilder`, `VisualNodeFactory`, `VisualGraphToAstConverter`, and `VisualNodeWidget`: `"Variable"` for the target-identifier DataIn port on IS APPOINTED, VICTIM IS APPOINTED, and PRAY TELL; `"Victim"` for the array-index DataIn port on VICTIM IS APPOINTED; `"Victim X"` (1-based, e.g. `"Victim 1"`, `"Victim 2"`) for array initial-value DataIn ports on PRAY WELCOME array nodes; `"Value"` for expression-value DataIn ports; `"Out"` for Identifier node DataOut ports. `HasArrayElementPorts` in `VisualNodeWidget` and the scanner both check for the `"Victim "` prefix (with trailing space) — maintain this prefix exactly.

**Visual editor — `ArrayElementLiteralType` vs `NodeLiteralType` on array declaration nodes**: `NodeLiteralType` is set to `LiteralType.Array` on array declaration nodes as a type marker (indicating "this is an array node"). `ArrayElementLiteralType` holds the actual element type (e.g. `LiteralType.Integer`). Code that displays the element type (scanner, widget element-type dropdown, converter) must read `ArrayElementLiteralType`, not `NodeLiteralType`. Reading `NodeLiteralType` on an array node always returns `Array` and will produce "LITTLE LIST" instead of the element keyword.

**Visual editor — `HasEditingControls` excludes `FINALE.` explicitly**: the editing-controls section is shown when `HasEditingControls` is true. The `VisualNodeKind.Program` check is guarded by `this.Node.Title != "FINALE."` because both `HARK!` (which has editable title/subtitle fields) and `FINALE.` (which has nothing editable) share `VisualNodeKind.Program`. Never remove this guard — adding edit fields to FINALE. would produce spurious converter input.

**Visual editor — `lastBuiltVisualSource` prevents feedback loops**: `Editor.razor` stores the last source string produced by the visual-to-code pipeline in `lastBuiltVisualSource`. `OnContentChangedAsync` compares incoming Monaco content against this field and skips `RebuildVisualGraphAsync` when they match, preventing the visual editor from re-building from its own output. Always set `lastBuiltVisualSource` before updating Monaco when triggering from the visual path.

**Documentation comment association rule**: `SymbolTable.FindDocumentationComment` scans backwards from the symbol's definition line to find an `END OF ASIDE.)` marker on the first non-blank line above the declaration. Blank lines between the block and the declaration are allowed; any non-blank, non-comment line breaks the association. Concretely: a doc comment inside a `PRINCIPALS` block must appear immediately before the `PRAY WELCOME` line it documents, not before the `PRINCIPALS` keyword itself.

**Documentation comment keywords in `KeywordData` (90 total)**: the 8 documentation tag keywords (`LEGEND:`, `RECITATIVE:`, `ARTICLE`, `CONSEQUENCE`, `CURSES`, `CHORUS:`, `ENSEMBLE:`, `STATUTORY:`) appear in the completion list but have no parser or runtime representation — they exist solely within `(ASIDE, AT SOME LENGTH: ... END OF ASIDE.)` blocks and are stripped by the `CommentsPreProcessor`. Do not add them to `Keywords.cs` or any parser combinator.

**`STATUTORY:` emits the `deprecated` semantic token modifier**: `SemanticTokensHandler` checks `symbol.Documentation?.IsDeprecated` and adds `"deprecated"` to the modifier list. The `Legend` now declares both `"readonly"` and `"deprecated"` modifiers. In VS Code, the `deprecated` modifier maps to strikethrough rendering via the `semanticTokenModifiers` contribution in `package.json` — add a `"deprecated"` entry there if the VS Code extension is updated to advertise the modifier.

**Web editor — semantic token provider uses a push model**: After each successful analysis pass, `ComputeSemanticTokenData` in `Editor.razor` encodes all symbol occurrences as a flat `int[]` (5 ints per token in Monaco's delta encoding: `deltaLine`, `deltaStartChar`, `length`, `tokenType`, `tokenModifiersBitmask`) and pushes it to JS via `topsyTurvy.setSemanticTokens(data)`. JS stores the array in `_semanticTokensData` and fires `_semanticTokensListeners`, causing Monaco to immediately call `provideDocumentSemanticTokens`, which returns the cached data as a `Uint32Array`. Token type indices: `variable`=0, `parameter`=1, `function`=2. Modifier bitmask: `readonly`=1, `deprecated`=2. Symbols whose names contain a space (e.g. `THE PROPS`) are skipped by the same guard used in `SemanticTokensHandler`.

**Web editor — semantic token scope hierarchy must use `variable.*`**: Monaco's `getTokenStyleMetadata` builds the TextMate lookup scope as `[tokenTypeName].concat(modifierNames).join('.')`. The built-in `vs-dark` TextMate trie has entries for `variable` and `variable.parameter` but not for bare `function`. Using `['variable', 'parameter', 'function']` as legend type names results in `function` tokens receiving no colour. All three legend type names therefore use the `variable.*` namespace (`variable`, `variable.parameter`, `variable.function`) so the trie resolves them correctly. The C# encoding does not change — it only emits integer indices.

**Web editor — semantic token theme rules must live in `enableSemanticHighlighting`**: `topsy-turvy-language.js` (Monarch tokenizer + base theme skeleton) can be served from the browser's HTTP cache between releases. `web-editor.js` is reliably fresh. `enableSemanticHighlighting` calls `monaco.editor.defineTheme` for both `topsy-turvy-dark` and `topsy-turvy-light` before enabling semantic highlighting. Redefining an already-registered Monaco theme also invalidates its internal `_tokenTheme` cache (Monaco calls `notifyBaseUpdated()`, which sets `_tokenTheme = null`), so the colours rebuild immediately from the new rules. `registerThemes` in `topsy-turvy-language.js` defines both themes with `rules: []`; the semantic token rules in `enableSemanticHighlighting` are always applied last and win.

**Ternary expression left-recursion guard — `NonTernaryExpression`**: `ExpressionParser` contains a `NonTernaryExpression` static field that is identical to `Expression` minus the `TernaryExpression` alternative. Both `TrueValue` and `Condition` in the ternary parser use `NonTernaryExpression`, not `Expression`. This prevents left-recursion (if `TrueValue` could itself be a ternary, the `TernaryExpression` parser would loop on itself) and prevents `OTHERWISE,` being consumed ambiguously mid-parse (a ternary in the condition position could consume `OTHERWISE,` before the outer ternary sees it). Only `FalseValue` uses full `Expression` via `Parse.Ref(() => Expression!)`, enabling right-chaining. Do not add `TernaryExpression` to `ExpressionStatementParser` — a bare ternary as a top-level statement would conflict with the `Conditional` statement parser, which also starts with `SHOULD IT TRANSPIRE THAT`.

**Guard clause formatter depth — `PostIncrease2` / `PreDecrease2`**: `YEOMAN` is in `SourceFormatter.PostIncrease2Keywords` (depth +2 after the line) and `UNDER ORDERS.` is in `PreDecrease2Keywords` (depth -2 before the line). This produces the same two-level indentation pattern as `IN WHICH CAPACITY?` / `NOTHING COULD BE MORE SATISFACTORY.`. `OTHERWISE,` inside a guard is already a `MidBlockKeyword` (depth -1 before, +1 after), matching its behaviour in `Conditional`.

**Assert `THAT` keyword is NOT in `KeywordData` but IS highlighted**: `THAT` is a structural separator within the `Assert` parser (`THE LAW IS <condition> THAT <errorMessage>`). It is intentionally absent from `KeywordData.Keywords` to avoid polluting the LSP completion list with an ambiguous fragment that also appears in `THAT WILL DO.` and `THAT CONCLUDES THE MATTER.`. The `Assert` parser matches it via `Lexer.Keyword("THAT")` inline — the keyword is only reachable after `THE LAW IS` has already matched. `THAT` is not added to `CanonicalKeywords` in `SourceFormatter`. It IS highlighted for syntax colouring in all three layers (REPL, Monaco, TextMate); in each case, all multi-word `THAT`-containing keywords are tried before the bare `THAT` rule (longest-match in REPL, rule order in Monaco and TextMate), so those longer keywords always win.

**`Keywords` class scope**: `Keywords.cs` in `BWHazel.TopsyTurvy.Ast` covers only strings used in code logic across multiple projects — literals (`VERITY`, `NAY`, `NAUGHT`), type names (`PEER`, `CHANCELLOR`, `PIRATE`, `SAUSAGE-ROLL`, `STANDING`, `FATHOM`, `FOOT`, `YARN`, `STITCH`, `DECREE`), and special names (`THE PROPS`). Single-site parser grammar strings such as `Lexer.Keyword("BEHOLD")` are intentionally left inline. `KeywordData.Keywords` in Analysis remains the authoritative 96-entry list for LSP/completion and must not be duplicated in `Keywords.cs`.

**Integer literal range is `int` only**: `Lexer.IntegerLiteral` delegates to `Numerics.IntegerInt32`, so literal values are capped at ±2,147,483,647. `CHANCELLOR` (`long`) and `STANDING CHANCELLOR` (`ulong`) variables cannot be initialised with out-of-range literals directly; assign a computed result or use casts. This is a Superpower limitation — adding a 64-bit literal parser would require a new combinator and changes to `ExpressionParser.LiteralExpression`.

**`STANDING` modifier is parsed inside `TypeKeyword`, not at the declaration level**: `ExpressionParser.TypeKeyword` tries `STANDING <base-integer-type>` as a `.Try()` alternative before any other type keyword. This means `STANDING` works automatically everywhere a type annotation is accepted: declarations, `IS HENCEFORTH A`, and `AS IT WERE … AS A`. `STANDING` followed by a non-integer type keyword (e.g. `STANDING FATHOM`) will silently fail the `.Try()` and fall through — it will NOT produce a parse error. `STANDING` alone as a type name is also not valid; the parser backtracks and reports a missing type keyword error.

**YARN string indexing — no parser changes**: `VICTIM n ON yarn` and `RECKONING OF yarn` reuse the `ArrayIndexNode` and `ArrayLengthNode` AST nodes unchanged. The runtime dispatches on `LiteralType.String` before the `LiteralType.Array` path in `EvaluateArrayIndex` and `EvaluateArrayLength`. `ExecuteArrayElementAssignment` checks `LiteralType.String` first and throws immediately — strings are always immutable by position in Topsy Turvy.

**Arithmetic widening uses `long` for all integer-family arithmetic**: `ApplyArithmetic` converts both operands to `long` via `ToLong()` before applying the integer operation, then converts the `long` result back to the widest operand type via `CreateIntegerFromLong`. This means unsigned arithmetic for `STANDING CHANCELLOR` (`ulong`) passes through `long`, potentially losing precision for values > `long.MaxValue`. Fix requires a separate unsigned arithmetic path if full `ulong` range arithmetic is ever needed.

**`ApplyArithmetic` signature changed from `Func<int,int,int>` to `Func<long,long,long>`**: all call sites in `EvaluateBinaryOperator` use lambda syntax `(a, b) => a + b` etc. which are type-inferred and compile for `long` without changes. If a future operator needs genuine `int` arithmetic, wrap the lambda explicitly.

**`FOOT` arithmetic result type**: `FOOT` (Single) + any integer type → result is `FOOT`. `FOOT` + `FATHOM` → result is `FATHOM` (the `LiteralType.Double` check fires before the `LiteralType.Single` check in `ApplyArithmetic`). Two `FOOT` operands → `FOOT`. The float path always computes through `double` internally; the `FOOT` path casts the `double` result back to `float`.

**`TopsyTurvyValue.CastTo` for new types routes through `long`/`ulong`/`double`/`char` helpers**: `CastTo` dispatches to private `ToInt64()`, `ToUInt64()`, `ToDouble()`, and `ToChar()` helper methods (on the value instance, not the static `Interpreter` helpers). The `Interpreter` has its own separate static `ToDouble(TopsyTurvyValue)` and `ToLong(TopsyTurvyValue)` helpers. The two sets are independent; keep them in sync if the type list changes.

**`SourceSpan` is a half-open interval**: `Start` is inclusive, `End` is exclusive — `End` points to the column one past the final character of the region, i.e. `[Start, End)`. This matches the LSP range convention used by the web editor. Confirmed by the error-span construction in `TryParse` (`endColumn + 1`).

**`PlaceholderSpan` is a fallback, not the default**: `ParserHelpers.PlaceholderSpan` (`(0,0)-(0,0)`) is returned by `BuildSpan` only when `ActiveSourceMap` is `null` — for example in isolated unit tests that call a parser combinator directly. During normal parsing via `TopsyTurvyParser.Parse`/`TryParse`, `ActiveSourceMap` is always set before the parse and all AST nodes receive real spans mapped from the pre-processed text back to the original source.

**`TypeCheckVisitor` pre-seeds `THE PROPS` in the root scope**: the `Visit` method pushes the root `scopeStack` frame pre-populated with `[Keywords.SpecialNames.TheProps] = LiteralType.Array` and the root `arrayElementTypeStack` frame pre-populated with `[Keywords.SpecialNames.TheProps] = LiteralType.String`.  Without this, valid programmes that reference `THE PROPS` (which is never declared via `PRAY WELCOME`) would receive an undeclared-name error from `InferIdentifier`.

**`TypeCheckVisitor` undeclared-name errors**: `InferIdentifier` emits an error and returns `null` when `LookupSymbol` finds no entry for the referenced name.  `CheckAssignment` emits an error and returns early when the assignment target is not in any scope frame (rather than silently skipping the type-compatibility check as it did before).  `CheckInput` emits an error and returns early when `PRAY TELL`'s target is undeclared.  `InferSummon` was already correct (it emits an error for unknown function names).

**`THE PROPS` exclusion**: `THE PROPS` contains a space, so the existing space-in-name check in `RenameHandler` and `PrepareRenameHandler` excludes it from rename automatically — no explicit check needed. It is pre-populated in `SymbolTable.Build()` with `IsConstant = true` and `TypeDisplayName = "CONSERVATIVE LITTLE LIST OF YARN"`, and excluded from semantic token colouring by the same space check in `SemanticTokensHandler`. Attempting to re-declare it with `PRAY WELCOME` is a runtime error (variable already declared).

**`THE PROPS` parser handling**: `THE PROPS` is a two-word token and cannot be matched by `Lexer.Identifier`. `ExpressionParser.ArrayNameParser` matches it explicitly (trying `Lexer.Keyword("THE PROPS")` first, then falling back to `Lexer.Identifier`) and is used wherever an array name appears in the parser — `ArrayIndexExpression` and `StatementParser.ArrayElementAssignment`. `ThePropsExpression` in the `Expression` chain handles bare references to `THE PROPS` (e.g. `BEHOLD THE PROPS`) and must appear before `IdentifierExpression` so that `THE` is not consumed as a plain identifier.

**`THE PROPS` CONSERVATIVE enforcement**: element assignment on `THE PROPS` follows the same path as any other `CONSERVATIVE` array — `ExecuteArrayElementAssignment` calls `environment.IsConstantInChain("THE PROPS")`, which returns `true`, and a `TopsyTurvyRuntimeException` is thrown. No special-casing is needed in the interpreter.

**LSP stdio**: `.ClearProviders()` must be called before `.AddLanguageProtocolLogging()` when configuring OmniSharp logging. Without it, the default console logger writes to stdout and corrupts the JSON-RPC stream. Configured in `IncantationCommandBuilder.HandleIncantationAsync()`.

**`--stdio` hidden option**: `vscode-languageclient` unconditionally appends `--stdio` to the process args when `TransportKind.stdio` is used. The `incantation` command registers `--stdio` as a hidden `Option<bool>` so `System.CommandLine` accepts it silently. Without this, the CLI rejects it as an unrecognised argument and the LSP server fails to start.

**`OmniSharpServer` alias in `IncantationCommandBuilder`**: `BWHazel.TopsyTurvy.LanguageServer` is both a project namespace (imported via `using`) and the name of OmniSharp's static server class. The alias `using OmniSharpServer = OmniSharp.Extensions.LanguageServer.Server.LanguageServer;` is required to disambiguate. Do not remove it.

**Bundled binary takes precedence**: `resolveCliPath` in `paths.ts` calls `fs.existsSync` on `bin/operetta` at activation time. Once `npm run prebuild:dotnet` has been run, the bundled binary is always used — re-run `npm run prebuild:dotnet` to refresh it, or delete `bin/` to force the dev-layout fallback.

**`DocumentStateManager`**: singleton; rebuilds `SymbolTable` only on a successful parse, preserving the last good table during syntax errors.

**`TryParse` reserved-word errors**: returns `ParseResult(program, errors)` with non-null `program` so the symbol table still builds while squiggle diagnostics are published. `Parse()` (used by the CLI) throws `TopsyTurvySyntaxException` instead.

**Visual editor — `ExpressionNodeTypes` HashSet controls drag and double-click routing**: `VisualEditor.razor` contains a `private static readonly HashSet<string> ExpressionNodeTypes` that lists every `StatementType` string that should be created as an expression node (via `VisualNodeFactory.CreateExpression`). Any type string **not** in this set is silently routed to `CreateStatement`, which returns an empty list for unknown types — the node simply does not appear on the canvas. When adding a new expression node type to the symbol panel or context menu, add its type string to `ExpressionNodeTypes`. Current contents: `"LiteralNode"`, `"IdentifierNode"`, `"OperatorNode"`, `"ArithmeticNode"`, `"BitwiseNode"`, `"LogicalNode"`, `"VariadicNode"`, `"WovenNode"`, `"TernaryNode"`, `"SummonNode"`, `"ArrayIndexNode"`, `"ArrayLengthNode"`, `"ExpressionCastNode"`.

**Visual editor — SUMMON node has both data ports and flow ports**: every SUMMON node (built by `VisualGraphBuilder` or `VisualNodeFactory`) has FlowIn "In", FlowOut "Out", DataIn "Function", DataIn "Arg X" ports, and DataOut "Out". When used as an expression, DataOut is wired to the consumer's DataIn and the flow ports are left disconnected. When used as a statement (for void-return function calls), FlowIn is wired from the previous flow node and FlowOut to the next — `WalkFlowStatements` then encounters it and `ReconstructSingleStatement` wraps it in `ExpressionStatement`. Both use cases call `ReconstructSummonFromNode` internally.

**Visual editor — ArrayIndex and ArrayLength use "Variable" DataIn port for the array name**: both `ArrayIndexNode` and `ArrayLengthNode` express the target array as an Identifier node connected to a DataIn port labelled "Variable" — the same pattern as IS APPOINTED and PRAY TELL. `GetTargetNameFromPort` is the canonical helper for reading the array name from this port in the converter. Factory-created nodes have the "Variable" port but no pre-wired Identifier node; the user drags a symbol from the Symbols panel and connects it. The `ArrayIndexNode` title is "VICTIM" (subtitle "at index"), not the array name.

**Visual editor — SUMMON argument ports live on the SUMMON node, not the function-name node**: the SUMMON sub-graph has two nodes — the outer SUMMON node and an inner SummonFunctionNode (the function name). Arg DataIn ports (`"Arg 1"`, `"Arg 2"`, …) are added to the **SUMMON node**; the SummonFunctionNode has only a DataOut. `VisualGraphToAstConverter.ReconstructSummonFromNode` reads the SUMMON node's DataIn ports, filters out `"Function"`, orders by label, and treats each as an argument. Do not add arg ports to the SummonFunctionNode.

**Visual editor — SUMMON architecture (Phase D)**: SUMMON has FlowIn "In", DataIn "Function", DataOut "Out", FlowOut "Out". The "Function" DataIn accepts a FunctionReferenceNode's DataOut. FunctionReferenceNode (created when dragging a function from the Symbols panel) has one named DataIn port per parameter and a single DataOut "Out". Arguments are wired into FunctionReferenceNode's DataIn ports, not SUMMON's. `ReconstructSummonFromNode` follows the "Function" DataIn → FunctionReferenceNode, then reads that node's DataIn ports for argument expressions. Do not add argument ports to SUMMON itself.

**Visual editor — FunctionReferenceNode is expression-typed**: `"FunctionReferenceNode"` is in `ExpressionNodeTypes` in `VisualEditor.razor`. It is routed through `VisualNodeFactory.CreateExpression`, not `CreateStatement`. Omitting it from `ExpressionNodeTypes` silently prevents the node from appearing on canvas when dragged from the Symbols panel.

**Visual editor — TERM parameter nodes use `VisualNodeKind.Parameter`, not `VisualNodeKind.Declaration`**: parameter TERM nodes are rendered in dark blue (`#1565c0`), distinct from green Declaration nodes. Both `VisualNodeWidget.AddParameter()` and `VisualEditor.CreateSymbolNode` (for `VisualSymbolKind.Parameter`) must set `Kind = VisualNodeKind.Parameter`. `VisualGraphBuilder.CreateFunctionBodySubgraph` also uses `VisualNodeKind.Parameter`. Using `Declaration` gives the wrong colour and may confuse the scanner.

**Visual editor — body-sync bug is fixed; never re-introduce `ReconstructBodyStatements`**: the retired helper `ReconstructBodyStatements(original.Body, diagram)` iterated the frozen original AST, ignoring all live graph edits made after the last parse. It has been removed. All builder-backed `Reconstruct*` methods now use `WalkBranchBody` or `WalkFlowStatements` to follow live port links. Do not re-introduce this pattern.

**Visual editor — `WalkFlowStatements` `skipFirst` semantics**: `skipFirst = true` (default) means the first node visited is `NextFlowNode(startNode)` — i.e. the node after `startNode` in the flow chain. `skipFirst = false` means `startNode` itself is the first statement to reconstruct — used when a branch-entry sentinel node IS the structural start of the body (no header node above it). `IsBranchHeaderSentinel` determines which case applies: it returns `true` for all 8 branch-header types, meaning those headers need `skipFirst = false` when passed as `startNode` to `WalkBranchBody`.

**Visual editor — symbol panel resize JS uses `initialWidth` parameter**: `window.visualSymbolPanel.startResize(startX, initialWidth, dotNetRef)` computes `initialWidth + (e.clientX - startX)` on each `mousemove`. The `initialWidth` argument must be the panel's current pixel width at the time the drag starts — captured from `this.panelWidth` in `OnResizeHandleMouseDown`. Do not hardcode the initial width to a constant inside the JS function.

**Visual editor — operator node port count on unary/binary switch**: `VisualNodeWidget.AdjustOperatorPortCount` only *adds* a missing second DataIn port when switching from a unary to a binary operator. It cannot *remove* extra ports — ZBD's `Ports` collection has no single-item `Remove` overload. The converter's `ReconstructOperatorFromNode` null-filters unconnected DataIn ports (lines where `GetExpressionSourceNode` returns null are skipped), so leftover ports are harmless.

**`EITHER` uses `OR` separator, not `AND`**: `EITHER x OR y` is the correct syntax per SPEC.md. The parser uses `SingleOrExpression` (a private parser that matches ` OR <expression>`) for the second operand of `EITHER`; all other non-variadic binary operators use `SingleAndExpression` (` AND <expression>`). The code generator emits `EITHER x OR y`. Any new test using `EITHER` must use `OR` as the separator.

**`SUMMON` call syntax**: `SUMMON name WITH arg1 AND arg2 IF YOU PLEASE.` / `SUMMON name WITH NOTHING IF YOU PLEASE.` — uses `WITH` as the argument separator, not `AND`.

**Blazor WASM timeout**: `CancellationTokenSource(TimeSpan)` relies on a timer callback that cannot fire while `Interpreter.Execute()` is blocking the single WASM thread. Set `ExecutionTimeout = TimeSpan.FromSeconds(10)` in `InterpreterExecutionOptions` instead — this stores a `DateTime` deadline checked by `CheckCancellation()` inside every loop body via `DateTime.UtcNow`.

**`PRAY ADMIT` path resolution**: `ExecuteImport` resolves relative import paths against the directory of the *importing* file, not the process CWD. `Interpreter.Execute()` accepts an optional `sourceFilePath` parameter; when `null` (e.g. Blazor WASM), the raw path from the AST is used unchanged.

**Web editor virtual FS resolver**: `Interpreter.Execute()` accepts an optional `Func<string, string?> fileResolver`. When supplied, `ExecuteImport` calls this delegate instead of `File.ReadAllText`, enabling `PRAY ADMIT` to resolve imports from the in-memory virtual filesystem. Import paths must be bare filenames — no directory prefix.

**Cross-document LSP awareness**: `DocumentStateManager.AllDocuments()` returns a snapshot of all open documents. Attempt lookup in the current document's `SymbolTable` first; on failure, iterate `AllDocuments()` skipping the current URI. For `DefinitionHandler`, the URI returned by the cross-file fallback must be used as `Location.Uri` in the response. Only `Function` kind symbols are pulled from other documents for hover, completion, and semantic tokens. `WorkspaceSymbolHandler` and `ReferencesHandler` aggregate across all documents unconditionally.

**Multi-word keyword completion**: `CompletionHandler` uses server-side phrase filtering, `FilterText = lastWord`, `InsertText = keyword[insertOffset..]`, `isIncomplete = true`, and a space trigger character to keep the list live as the user types through multi-word phrases.

**Web editor — localStorage single-key merge pattern**: all editor preferences are stored under one key (`topsy-turvy-editor`) as a merged JSON object. `savePreferences(preferences)` always reads the existing object first and spreads the incoming partial update over it (`{ ...existing, ...incoming }`). This lets JS-managed keys (split ratios `horizontalSplit`, `verticalSplit`) and C#-managed keys (files, active file, dark mode, etc.) be written independently without clobbering each other. The C# side calls `topsyTurvy.loadPreferences()` (returns the full object) and `topsyTurvy.savePreferences(EditorPreferences)` via `JSRuntime`. Blazor's JS interop layer serialises `EditorPreferences` to/from JSON using `System.Text.Json`, respecting `[JsonPropertyName]` attributes on the class and `[JsonConstructor]`/`[JsonPropertyName]` on `VirtualFile`.

**Web editor — `[JsonConstructor]` on `VirtualFile` is required for round-trip deserialisation**: `VirtualFile.Name` has no setter (it is set only via the constructor). Without `[JsonConstructor]`, `System.Text.Json` cannot deserialise JSON into a `VirtualFile` instance and throws. The attribute must remain on the constructor. Parameter names in the constructor must match the `[JsonPropertyName]` values on the corresponding properties (case-insensitive) — `System.Text.Json` matches by convention.

**Web editor — terminal theme not applied dynamically by XtermBlazor**: XtermBlazor reads `Options` only once at initialisation. Two mechanisms are therefore needed: (1) `terminalOptions` in `Editor.razor` is an expression-bodied property (not a `readonly` field) that reads `this.IsDarkMode`, ensuring the correct theme is applied on first render since the `IsDarkMode` cascading parameter is set before the first `OnAfterRenderAsync`; (2) `topsyTurvy.setTerminalTheme(isDarkMode)` is called from `OnParametersSetAsync` whenever the theme changes, updating `term.options.theme` directly on the xterm instance. Terminal colours: dark mode — background `#1e1e1e`, foreground `#d4d4d4`; light mode — background `#f5f5f5`, foreground `#1e1e1e`.

**Web editor — terminal output persistence via `lastRunOutput`**: `lastRunOutput` accumulates output lines joined by `\n`. It is saved as `TerminalOutput` in `EditorPreferences` after every run (in the `finally` block of `RunProgramAsync`) and after clear (`ConfirmClearAsync`). It is reset to `string.Empty` at the start of `RunProgramCoreAsync` (right after `terminal.Clear()`) so a failed run does not persist stale output from a previous successful run. On restore, `TerminalOutput` is split on `'\n'` and each line is replayed via `terminal.WriteLine`.

**Web editor — preference save triggers**: `SavePreferencesAsync` is called from: `OnContentChangedAsync` (the 400 ms debounce path, after syncing the active file's `Content`), `@bind-Value:after` on both `MudTextField` elements (CLI args and stdin), `OnGsLabelsToggledAsync` (G&S labels switch), `OnParametersSetAsync` when dark mode changes, the `finally` block of `RunProgramAsync` (after every run including failures), and `ConfirmClearAsync` (after terminal is cleared).

**Web editor — preference restore order in `RestorePreferencesAsync`**: G&S labels → CLI args → stdin → files (clear list, add each, build symbol table) → active file (set `activeFileName`, call `monacoEditor.SetValue`) → terminal output (replay lines, set `lastRunOutput`) → dark mode (call `ToggleDarkMode?.Invoke()` only when stored value differs from current). `StateHasChanged()` is called at the end. Restore is invoked from `OnAfterRenderAsync` on first render, after `initPaneDrag` and before `editorReady = true`.

**Web editor — terminal fit private API**: `fitTerminal` reads `term._core._renderService.dimensions.css.cell.height`. This is an internal xterm.js property — if the terminal stops filling its pane after an XtermBlazor upgrade, check this path first.

**Web editor — editor content API**: per-file content is stored in `VirtualFile.Content` and loaded/saved via `monacoEditor.SetValue` / `blazorMonaco.editor.getValue`. URI-based Monaco models were considered but abandoned — replacing BlazorMonaco's default model breaks the `onDidChangeModelContent` event system.

**Web editor — output download**: `Editor.razor` stores the last run's output in `lastRunOutput`. `DownloadTerminalAsync` uses this field directly rather than reading the xterm buffer. `lastRunOutput` is reset when the terminal is cleared via `ConfirmClearAsync`.

**Web editor — open file replace**: `OpenSingleFileAsync` handles the case where the opened file shares a name with an already-open tab. When the replaced file is the active tab, call `monacoEditor.SetValue(content)` directly — do not call `SwitchFileAsync`, which would re-sync old content back over `VirtualFile.Content`.

**`CONSERVATIVE` constant enforcement**: `IS APPOINTED` (assignment) and `PRAY TELL` (input) both ultimately call `TopsyTurvyEnvironment.Assign`, which checks `this.constants.Contains(name)` before allowing the write — the constraint is enforced centrally. `AS IT WERE` does not need a guard because it produces a new value without mutating the source variable.

**`LITTLE LIST OF` in the parser, not `A LITTLE LIST OF`**: In the source text `AS A LITTLE LIST OF YARN`, the phrase `AS A` is consumed by `Lexer.Keyword("AS A")` — this matches exactly 4 characters `A-S-space-A`, positioning the cursor immediately after the final `A`. The remaining token stream therefore starts with ` LITTLE LIST OF`, not ` A LITTLE LIST OF`. The array-type combinator must match `Lexer.Keyword("LITTLE LIST OF")`. Using `Lexer.Keyword("A LITTLE LIST OF")` will fail to match because the `A` was already consumed. This applies in `StatementParser.ArrayDeclaration`, `ExpressionParser.ExpressionCast`, and anywhere else `AS A` is followed by an array type. `GRAMMAR.ebnf` carries an explanatory comment on the `ArrayDeclaration` production.

**`RECKONING OF` is an expression, not a statement, and must appear in `ExpressionStatementParser`**: `ExpressionStatementParser` in `StatementParser.cs` has its own explicit list of expression alternatives (distinct from `ExpressionParser.Expression`). Any new expression that can appear as a standalone statement must be added to **both** lists. `ArrayLengthExpression` is included in both. Omitting it from `ExpressionStatementParser` causes a `TopsyTurvySyntaxException` when parsing a bare `RECKONING OF arr` as a statement, even though the parser itself is correctly wired. `RECKONING OF` is read-only — it does not trigger `IsConstantInChain` and works on `CONSERVATIVE` arrays without error.

**Array element assignment bypasses `TopsyTurvyEnvironment.Assign`**: `VICTIM n ON arr IS APPOINTED val` mutates the `List<TopsyTurvyValue>` stored inside the array value directly — it does not call `Assign`. The standard CONSERVATIVE guard in `Assign` is therefore never triggered. Instead, `ExecuteArrayElementAssignment` calls `environment.IsConstantInChain(arrName)` (which walks the enclosing scope chain) before mutating the list. Do not rely on `Assign` for constant enforcement in array element mutations.

**Sized array size+BEING mutual exclusivity is a runtime error, not a parse error**: When `ArrayDeclarationNode.Size` is non-null and `InitialValues.Count > 0`, `ExecuteArrayDeclaration` throws a `TopsyTurvyRuntimeException`. The parser does not prevent this combination — it happily parses `PRAY WELCOME arr AS A LITTLE LIST OF 3 PEER BEING 1 AND 2 AND 3 IF YOU PLEASE.` into an `ArrayDeclarationNode` with both `Size = 3` and three `InitialValues`. The guard lives exclusively in the runtime. Similarly, a negative size is caught only at runtime.

**Array reference semantics**: `PRAY WELCOME alias AS A LITTLE LIST OF PEER` followed by `alias IS APPOINTED original` makes both variables point to the same `List<TopsyTurvyValue>` instance. Mutating an element via `alias` is visible via `original` and vice versa. There is no copy-on-assign. This is consistent with how .NET reference types work and is intentional — value semantics for arrays are deferred to a future struct/class type system.

**1-based array indexing and ascending loops**: `VICTIM 1 ON arr` accesses the first element. The ascending loop (`BY A LEGAL FICTION ASCENDING x UNTIL n`) resets its counter to 0 at the start of each iteration — using it to index into an array would start at `VICTIM 0`, which is out-of-range. Use a WHILST loop for array traversal: `count IS APPOINTED 1`, then `BY A LEGAL FICTION WHILST HARDLY EVER PRE-ADAMITE count AND length`, incrementing `count` manually inside the loop body. See `examples/language/arrays.topsy` for the canonical pattern.

**`AS IT WERE` is an expression, not a statement**: `AS IT WERE <expr> AS A <type>` is parsed as an `ExpressionCastNode` (extends `Expression`).  When used as a standalone statement it is wrapped in an `ExpressionStatement`; the type checker emits a warning for the discarded return value.  There is no `ExecuteExpressionCast` method — cast evaluation is handled entirely inside `EvaluateExpression`.

**Try/catch inline expression**: `WITH THE GREATEST RESPECT, <expression>` requires the expression on the *same line* as the keyword. Writing it on the following line causes a parse failure. The formatter's indentation rules for this construct diverge from valid parser input by design.

**`MODIFIED RAPTURE` catch binding is mandatory and creates a child scope**: the parser requires `MODIFIED RAPTURE, Name` — the binding is not optional.  The interpreter calls `environment.CreateNested()` and declares `Name` as a `YARN` variable in that child scope.  The binding is inaccessible outside the exception block — accessing it after `THAT CONCLUDES THE MATTER.` produces a runtime error.  The comma delimiter (`MODIFIED RAPTURE, Name`) is required to avoid ambiguity with statement-starting identifiers (e.g. `result IS APPOINTED ...`) that the parser would otherwise greedily consume as the binding name.

**Web editor — MudTabs API (MudBlazor 9.x)**: `ScrollButtons` was renamed to `AlwaysShowScrollButtons`. `PanelClass` belongs on `MudTabPanel`, not `MudTabs`. Using the old names produces MUD0002 analyzer warnings.

**Web editor — auto-indent**: Monaco's `indentationRules` only take effect when `autoIndent` is `'full'` (numeric `4`). This is a construction-time option — set via `AutoIndent = "full"` in `StandaloneEditorConstructionOptions`; `updateOptions` has no effect on it.

**CLI version string**: `AssemblyInformationalVersionAttribute` = `{Version}+{SourceRevisionId}`. `PedigreeCommandBuilder` splits on `+` and holds `SpecVersion = "0.2.0"` as a private constant.

**`--tiptoe` output routing**: with `--tiptoe`, errors go to stderr and program output to stdout. Without it, all output — including error panels — goes to stdout via `AnsiConsole.Write`. E2E tests that assert on error messages must use `--tiptoe`.

**Spectre.Console panel header truncation in non-TTY mode**: when stdout is redirected, Spectre.Console truncates panel headers to fit the content width with a Unicode ellipsis (`…`). A short body (e.g. a short filename) produces a narrow panel. Workaround: use a long filename to widen the panel, or assert only the unambiguous prefix.

**SignatureHelp two-update pattern**: signature help tests for in-progress `SUMMON` calls (where `IF YOU PLEASE.` has not been typed yet) must seed `DocumentStateManager` with a successful parse before updating with the incomplete source, so the last-good symbol table is preserved and available to the handler.

## 4. Known Gaps

**`PrincipalBlockNode.Declarations` uses a weak base type instead of a discriminated union**: `Declarations` is typed as `IReadOnlyList<Statement>` rather than a union of `DeclarationNode | ArrayDeclarationNode`, because C# does not yet provide first-class discriminated-union syntax. Callers must pattern-match at runtime to determine the concrete type. This will be revisited when discriminated unions land in C# / .NET 11.

**Ascending loop always starts from 0 (spec-level limitation)**: `ASCENDING <var>` resets the loop variable to `0` at the start of every loop per the spec (`<var>` begins at `0`). There is no syntax to specify a different starting value. Descending loops have no such constraint — they use the variable's current declared value. Fix requires a spec change (remove the "begins at `0`" constraint, or add `FROM <n>` syntax) and removing the hardcoded `Assign(..., Integer(0))` in `ExecuteAscendingLoop`.

**Monarch tokenizer keyword duplication**: the keyword list appears in `topsy-turvy-language.js` (Monarch tokenizer) and `topsy-turvy.tmLanguage.json` (TextMate grammar). The JS and TextMate copies cannot consume the C# library and remain separate. When adding a language feature, update both in the same change.

**Web editor interactive stdin (deferred)**: `BufferedWebIO` reads from a pre-supplied `Queue<string>`. True interactive stdin requires making `ITopsyTurvyIO` async — a new `InteractiveWebIO` implementation and an XtermBlazor input handler.

**LSP squiggle accuracy — Option 1 done, Option 2 deferred**: syntax errors now report at the correct line. The `WsMany<T>` combinator in `ParserHelpers` replaced all 12 `Ws(X).Try().Many()` block-body sites; it separates whitespace consumption from the statement parse and propagates partial-match errors (where an opening keyword was consumed but the body failed) at the actual failure position rather than resetting the cursor. `TryParse()` still stops at the **first** syntax error — there is no error-recovery or multi-error reporting. Option 2 (deferred): full multi-error recovery requires a hand-written recovery loop that records the error, advances the cursor to the next statement-opening keyword, and continues; this is significant additional work and should be considered after static typing is introduced (more complex constructs = larger recovery surface area).

**`ValidateSymbolNames` only checks top-level statements**: `TopsyTurvyParser.ValidateSymbolNames` walks only the top-level statement list of `ProgramNode`. Declarations nested inside function bodies, conditionals, loops, or try-catch blocks are not validated — a variable declared with a reserved-keyword name inside a nested block will not produce a diagnostic. Note that the parser may independently reject some of these cases (reserved words that cannot be lexed as identifiers), but the semantic check is incomplete by design. Fix requires recursing into all block-bearing statement types (`FunctionDefinitionNode`, `ConditionalNode`, `LoopNode`, `TryCatchNode`, etc.) or introducing an AST visitor.

**Web editor JS not linted or formatted**: `topsy-turvy-language.js` and `web-editor.js` have no ESLint or Prettier configuration.

**VS Code extension file icon**: the `icon` field on the `languages` contribution is only shown when no file icon theme is active. Long-term fix: submit a PR to `vscode-icons` adding a `.topsy` entry.

**`<example>` must be nested inside `<remarks>` for dotnetmd rendering**: the standard XML doc convention places `<example>` as a top-level sibling of `<summary>`, but dotnetmd only renders examples when `<example>` is nested inside `<remarks>`. Methods with no `<param>` tags (e.g. `TopsyTurvyValue.Null()`) and `override` methods (e.g. `TopsyTurvyValue.ToString()`) are additionally prone to their documentation being silently dropped. The non-standard placement must be maintained until dotnetmd is replaced or this behaviour changes upstream.


**Visual editor classes have no unit tests**: `VisualGraphBuilder`, `VisualGraphToAstConverter`, `VisualNodeFactory`, and `VisualTypeMaps` contain significant pure logic that is independently testable without a Blazor rendering context (Z.Blazor.Diagrams model types are plain C# objects). Tests should live in `Tests/Visual/VisualEditorTests.cs`; if the test project cannot reference the WASM-target WebEditor project, extract the `Visual/` classes into a non-Blazor class library `BWHazel.TopsyTurvy.WebEditor.Visual`. Coverage targets: `VisualGraphBuilder` (HARK! node presence, link wiring), `VisualGraphToAstConverter` (round-trip: parse → build → convert → generate → re-parse → diagnostics empty), disconnected DataIn port handling, `VisualNodeFactory` (correct `Kind`, `StatementType`, port roles; block types yield paired opener+closer). Follow the Shouldly assertion style from `TopsyTurvyCodeGeneratorTests`.

**`dotnetmd` cannot document LSP handlers and has additional rendering defects**: `dotnetmd` silently skips any class whose base type cannot be resolved from locally available XML documentation files. All Language Server handlers inherit from OmniSharp base classes (e.g. `HoverHandlerBase`, `CodeLensHandlerBase`) in NuGet packages that do not ship XML docs, so `dotnetmd` drops all handler pages without warning — only `DocumentStateManager` (base type `Object`) and other non-handler types survive. Additional defects: `<c>` inline code tags are not converted to Markdown backticks (rendered as literal `<c>text</c>` in output); `<remarks>` content is run together without line breaks. `DefaultDocumentation` (`scripts/generate-api-docs.sh`) is a working alternative: it documents all public types including handlers and processes the full XML doc set correctly. However, switching requires migrating all XML documentation comments from the project's current inline Markdown style (raw `*` bullet syntax, backtick spans, and other Markdown embedded within `<remarks>`) to standard .NET XML doc tags (`<list type="bullet"><item>`, `<c>`, `<para>`, etc.), because `DefaultDocumentation` treats XML node content as plain text rather than Markdown. Namespace title formatting in `DefaultDocumentation` output also differs from the current Docusaurus page structure and would require post-processing refinement before the generated pages are publication-ready.

**`SymbolTable` uses a flat namespace — parameters from different functions collide**: `SymbolTable` is a single `Dictionary<string, SymbolInfo>` (case-insensitive). If two functions declare a parameter with the same name (e.g. both have a parameter called `name`), only the first is kept; the second is silently dropped by the `ContainsKey` guard in `AddFunction`. Consequences: hover, go-to-definition, and rename all use the first function's definition position for any subsequently declared parameter of the same name, and Find All References aggregates occurrences from both functions under one symbol. Fix requires scoped symbol tables — a global scope for variables and functions, plus a per-function scope for parameters — and updates to all LSP handlers and web editor bridge methods that call `TryGetSymbol`.

| Feature | Blocker |

**Imported functions are surfaced in the visual symbol panel but flagged as undeclared in Monaco**: When `PRAY ADMIT "file.topsy"` is in the diagram, `Editor.razor.GetImportedFunctionSymbols` parses the imported file and adds its functions to the symbol panel so users can drag them onto the canvas. However, when the generated source is analysed by the LSP / type checker, the function is genuinely undeclared in the current file's symbol table — the cross-document function lookup that works in the LSP does not apply during the visual editor's local analysis pass. Fix requires either (a) building a merged symbol table that includes imported file symbols before the visual-editor analysis pass, or (b) extending `TopsyTurvyTypeChecker` to resolve cross-file symbols via the virtual file system resolver already present in `Interpreter`. This is a type-checker / analysis-layer change, not a visual-editor change.
